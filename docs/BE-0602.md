# เปิดใช้ API ประเภทคูปอง

BE-0602 เพิ่ม `POST /v1/coupon-types` และ `GET /v1/coupon-types` ตาม [issue #222](https://github.com/najaroenx/blockchain-reward-platform/issues/222) วันที่ 4 พฤศจิกายน 2026

## รัน migration

ใช้ PostgreSQL สำหรับการทดสอบก่อนรันกับข้อมูลจริง

1. รัน `prisma/migrations/0001_init/migration.sql` หากยังไม่มี schema กลาง
2. รัน `prisma/migrations/0002_coupon_type_start/migration.sql` หนึ่งครั้งด้วย migration runner ของระบบ

สำหรับฐานข้อมูลที่ยังไม่มีประเภทบน chain migration จะเติม `starts_at` ของข้อมูลเดิมด้วย `created_at` ข้อมูลใหม่ต้องส่ง `startsAt` จาก request เสมอ

หากมีประเภทบน chain ให้อ่าน `getCouponData(chainTypeId).startDate` จาก contract ที่ตรงกับแต่ละแถว แล้วเตรียมข้อมูลใน PostgreSQL session เดียวกับ migration:

```sql
CREATE TEMP TABLE coupon_type_start_backfill (
  coupon_type_id text PRIMARY KEY,
  starts_at timestamptz NOT NULL
);

-- แทน ID และ timestamp ด้วยข้อมูลที่ตรวจจาก contract จริง
INSERT INTO coupon_type_start_backfill VALUES ('ct_existing', to_timestamp(VERIFIED_START_DATE_SECONDS));
```

จากนั้นรัน migration ใน session เดิม เช่นใช้ `\i prisma/migrations/0002_coupon_type_start/migration.sql` ใน `psql` หากข้อมูลวันเริ่มบน chain ไม่ครบ migration จะ rollback แทนการเดาวันใหม่ หากใช้ runner ที่เปิด connection ใหม่ ให้เขียนขั้นตอน staging นี้ใน deployment runner ก่อนรัน SQL บน connection เดียวกัน

อย่ารัน migration ใหม่ซ้ำโดยตรง ให้ migration runner บันทึกว่ารันแล้ว ใช้ feature flag ปิด route เมื่อต้องถอยกลับ การปิด route ไม่ลบ operation หรือ outbox ที่รับไว้แล้ว

## ตั้งค่า API

ค่าเริ่มต้น `COUPON_TYPES_ENABLED=false` ทำให้ route ยังไม่ถูกลงทะเบียน ใส่ค่าต่อไปนี้ใน environment ของ API เพื่อเปิด route:

```dotenv
COUPON_TYPES_ENABLED=true
COUPON_JWT_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----
...SPKI PEM ของระบบออก access token...
-----END PUBLIC KEY-----"
COUPON_JWT_ISSUER=https://auth.example.com
COUPON_JWT_AUDIENCE=reward-api
COUPON_RPC_URL=http://localhost:8545
COUPON_CHAIN_ID=31337
```

ใช้ `DATABASE_URL` เดิมสำหรับ PostgreSQL การเปิด feature โดยไม่มี config ครบทำให้ API ปฏิเสธการเริ่มทำงาน

Verifier รองรับ access token แบบ RS256 และตรวจ issuer, audience, signature และ expiry ต้องมี claims `sub`, `kind=MERCHANT_ADMIN`, `mid`, `sid`, `iat`, `exp`, `jti` ตามชื่อใน FEAT-03 reference ระบบออก token และการจัดการ session เป็นงาน auth แยกต่างหาก ไม่รับ merchant ID จาก header หรือ body แทน token

เริ่ม API ด้วย `pnpm dev:api` ใช้ [OpenAPI](api/coupon-types.openapi.json) และ [Postman collection](api/coupon-types.postman_collection.json) สำหรับรูปแบบ request และ response ตั้ง `baseUrl` และ `accessToken` ใน collection ก่อนรันตามลำดับ Create, Replay, List

## ตรวจการทำงาน

```bash
pnpm typecheck
pnpm lint
pnpm test
```

ชุดทดสอบคูปองเปิด PostgreSQL จริงจาก `embedded-postgres` ใน temporary directory และยิง HTTP ผ่าน NestJS ไม่ใช้ฐานข้อมูลจาก `.env` เครื่องต้องอนุญาตให้รัน binary ของ PostgreSQL และเปิด localhost port ชุดทดสอบ RPC ใช้ server fixture เพื่อทดสอบ ABI และการรับมือ error ไม่ใช่หลักฐานการ deploy หรือการทำงานกับ chain จริง

การทดสอบครอบคลุม request ซ้ำพร้อมกัน 20 รายการ, merchant isolation, ชื่อซ้ำ, ร้านไม่ ACTIVE, timezone, ช่วงวันที่, rollback เมื่อเขียนคิวล้ม และ migration บนข้อมูลเดิม

## ขอบเขตของ implementation

POST เขียน idempotency key เป็นคำสั่งแรกหลัง `BEGIN` แล้วบันทึกประเภท, operation, step, outbox และ event ใน transaction เดียว Response ที่รับไว้ถูกบันทึกเพื่อ replay ด้วยรูปแบบเดิม แม้วันหมดอายุจะผ่านไประหว่าง retry โค้ดนี้ใช้ idempotency เฉพาะ endpoint นี้ ยังไม่ใช่ middleware กลางของ #147 และไม่มีงาน cleanup key ที่หมดอายุ

Payload คิว topic `coupon.type.create.v1` มี `startDate` และ `expireDate` เป็น string ของ Unix timestamp หน่วยวินาทีสำหรับ `createCouponType(name,startDate,expireDate)` ส่วน `faceValue` และ `totalSupply` เป็นข้อมูลธุรกิจ ไม่ใช่พารามิเตอร์ของฟังก์ชันนี้

GET อ่าน supply ด้วย `getTotalSupply(typeId)` เมื่อมี chain projection เพราะโมเดลใหม่ไม่ใช้แถว `coupon_code` นับจำนวน ค่า contract นี้เพิ่มตอน mint ลดตอน withdraw ด้วย burn และไม่ลดตอน redeem จึงใช้เป็น `issuedCount` ที่ยังไม่ถูกถอน หาก chain อ่านไม่ได้ คืน 503 หากจำนวนเกินเพดานใน DB คืน `COUPON_SUPPLY_INCONSISTENT` ไม่แสดงจำนวนคงเหลือที่ผิด

GET อ่าน supply ล่าสุดจาก chain ไม่ใช่ snapshot ที่ยืนยัน finality แล้ว การเปลี่ยนเป็น projection ที่รองรับ reorg เป็นงาน indexer แยกต่างหาก ข้อมูลประเภทที่ยังไม่มี chain มี `chain=null`, `issuedCount=0` และ `remainingSupply=totalSupply` หากเป็น LIVE หรือ RETIRED แต่ไม่มี chain projection จะคืน 503

Worker และ indexer ใน repo นี้ยังเป็น placeholder จึงยังไม่ส่ง transaction หรือเปลี่ยนสถานะเป็น LIVE จาก outbox ระบบพร้อมสำหรับชั้น ADMIT และการอ่านประเภทที่มี projection อยู่แล้ว การออกหรือสร้างรหัสใน contract และการปรับ schema รหัสตาม #212 อยู่นอกใบนี้

ยังไม่ยืนยันว่า #147 หรือ #212 เสร็จแล้ว และยังไม่ได้ deploy ไปยังสภาพแวดล้อมทดสอบที่ใช้ร่วมกัน
